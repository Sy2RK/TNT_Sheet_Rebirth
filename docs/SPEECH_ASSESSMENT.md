# 语音识别检查与 ASR 接入评估

日期：2026-10-04。用户反馈：Chrome 已允许麦克风，但未成功识别，也没有出现文字。

后续已使用用户提供的百炼 Key 完成六个 ASR 模型的合成音频测试，详情见 [千问 ASR 评测](ALIYUN_ASR_EVALUATION.md)。本文件中“尚未实测”的描述为新增 Key 之前的检查记录；当前推荐优先验证最新 Message，其次 Streaming，并保留 Fun-ASR 和 Paraformer 作为对照。应用语音按钮仍使用 Web Speech。

## 结论

当前项目没有接入专用 ASR。浏览器的 Web Speech 是唯一语音转文字来源；DeepSeek 只在收到识别文字后理解表格指令。配置 DeepSeek Key 不会修复语音转文字。DeepSeek 官方目前声明 Flash 接受文本和图像，不声明音频输入，参见[模型列表](https://api-docs.deepseek.com/api/list-models/)。

Chrome 麦克风授权成功只代表可以采集音频，不代表远端识别服务可以工作。Web Speech 在 Chrome 的默认实现涉及服务端识别，参见 [MDN](https://developer.mozilla.org/en-US/docs/Web/API/SpeechRecognition)。不能仅凭“无文字”确定是网络、输入设备还是启动时序问题。

## 已确认的代码问题与修复

1. 旧版在 `start()` 调用返回后立即显示正在聆听，没有等待识别服务的 `start` 事件。现在区分连接、聆听、等待最终文字三个阶段。
2. 用户松手、原生表格事件及 document 事件可能重复调用 `stop()`，甚至发生在授权或服务启动之前。现在只发送一次停止请求，启动前松手会记录停止意图，等待启动后结束；首次授权仍应先完成授权，再重新按住说话。
3. 服务结束但结果为空、只有临时文字、或一直没有结束事件时，旧版可能无声退出或一直显示聆听。现在明确提示空结果、未确认文字、启动超时和最终结果超时。
4. 旧会话取消后仍可能收到迟到的识别事件。现在隔离会话、清理事件和计时器，迟到事件不更新文字或提交指令。
5. 现在错误消息保留浏览器错误码，便于区分设备、权限、网络和语言故障；未确认的文字不自动执行表格操作。

## 检查证据与边界

- 原有语音端到端测试使用伪造的 SpeechRecognition，只证明选区锁定、文字显示和 AI 路由，不证明真实麦克风或 Chrome 识别服务可用。
- 临时安装版 Chrome 154 的测试确认：localhost 是安全上下文、SpeechRecognition 存在、合成音频采集可以创建音轨，并出现 `start`、`audiostart`、`no-speech`、`end` 事件。
- 本地合成中文测试未取得结果，同样返回 `no-speech`。浏览器模拟音频可能未被识别引擎实际消费，不能据此断言中文服务不可用、网络被屏蔽或用户麦克风损坏。
- 没有录制用户的真实声音，没有修改用户浏览器权限，也没有得到用户当前会话的识别错误码。因此用户环境的最终根因尚未证实。

## 下一次真实测试的判别方法

使用 localhost 或 HTTPS；在 Chrome 和 Windows 中确认输入设备与输入电平。按住麦克风，等到“正在聆听”再说短句，松开后等待结果。

| 现象或错误码                     | 应检查的位置                                             |
| -------------------------------- | -------------------------------------------------------- |
| 长时间正在连接、启动超时         | 授权是否完成，浏览器是否真正启动了识别服务               |
| `not-allowed`                    | Chrome 站点授权、Windows 麦克风隐私权限                  |
| `audio-capture`                  | 输入设备连接与 Chrome 所选麦克风                         |
| `no-speech`                      | 输入音量、静音、错误输入设备、实际讲话时是否已经开始聆听 |
| `network`                        | 浏览器远端语音服务的网络可达性；与 DeepSeek 接口独立     |
| `service-not-allowed` 或语言错误 | 浏览器政策、服务或语种支持                               |
| 有临时文字但无最终文字           | 浏览器服务的结果完成流程，应用会保留文字在提示中但不执行 |

## 是否需要专用 ASR

对于临时演示，Web Speech 可以保留。对于把中文 Touch and Talk 作为核心交互、需要稳定实时出字的产品，建议接入可控的流式 ASR，把 Web Speech 留作可选方案。专用 ASR 能改善服务可控性、语种和术语支持、实时事件与错误诊断，但不能替代麦克风授权，也不能修复无音频输入。

| 方案              | 收益                                 | 代价与边界                                             |
| ----------------- | ------------------------------------ | ------------------------------------------------------ |
| 浏览器 Web Speech | 无需额外服务配置，适合快速试用       | 服务和浏览器差异难控制，实时结果与可用性缺少产品级保证 |
| 云端流式 ASR      | 实时文字、独立诊断、可配置语种和热词 | 新的凭证、音频时长费用、联网、音频发送给所选服务商     |
| 本地部署 ASR      | 可离线，音频保留在设备或自有服务     | 模型部署、硬件资源、维护及实时性能调优                 |

优先验证阿里云 `fun-asr-realtime`，另一个候选是豆包流式 ASR。Fun-ASR 的[模型文档](https://help.aliyun.com/en/model-studio/asr-model)列出流式 WebSocket、热词及中文/英文支持；其[结果事件](https://help.aliyun.com/en/model-studio/fun-asr-server-events)区分临时和最终文字。豆包也提供[流式识别](https://docs.volcengine.com/docs/DoubaoVoice/model-list?lang=en)。这里是根据接口特征提出的候选建议，尚未进行准确率、延迟或真实网络对比测试。

## 推荐接入结构

浏览器麦克风采集 → 连续音频分片 → 小型服务端或本地中转 → ASR → 临时/最终文字 → 现有 OperationEngine → DeepSeek → Univer。

继续使用已有 SpeechAdapter 边界，让 ASR 与 LLM 独立配置，分别保存服务、地址、模型、语言和会话内密钥。不要把 ASR Key 与 DeepSeek Key 混用。

优先流式识别以满足“边说边显示”，仅在松手后上传整段音频的实现无法满足实时文字需求。松手后需发送结束音频标记并等待最终结果，然后提交一次指令；取消时释放音轨并忽略迟到结果。

以 Fun-ASR 为例，官方 [WebSocket 文档](https://help.aliyun.com/en/model-studio/fun-asr-realtime-websocket-api)要求握手时添加 Authorization。浏览器原生 WebSocket 不能任意设置这类请求头，当前纯前端项目通常需要新增中转服务或使用服务商明确支持的短期令牌方案；不能简单复制当前 LLM 的 fetch 适配器。中转只处理识别和认证，表格内核及 AI 撤销事务可保留。

接入前的验收应使用真实 Chrome/Edge 和手机、中文/中英混合短指令、实际表格术语；测量启动耗时、首段文字延迟、松手后最终结果延迟、识别错误和错误执行率，同时验证取消、掉线及资源释放。本次仅修复现有 Web Speech 生命周期和提示，没有接入或开通收费 ASR。
